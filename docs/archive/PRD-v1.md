## 0. 现状盘点：我们手里到底有什么

设计一切的前提是把「已有能力」和「尚不具备的能力」分开。混淆这两者是本产品最大的可信度风险来源。

### 0.1 已确认具备的模型能力

| 能力族 | 具体维度 | 输出形态 | 备注 |
|---|---|---|---|
| 整体质量 | 全图 IQA 总体评价 | 标量分数 + 文本解释 | 唯一同时给分和给解释的模型，是「可解释性」的主要来源 |
| 美学与构图 | 美学 / 构图 | **假设**：分数为主，是否带文本解释未知（见开放问题 Q2） |  |
| 光影色彩 | 曝光 | 分数 | |
| 光影色彩 | 对比 | 分数 | |
| 光影色彩 | 白平衡 | 分数 | |
| 光影色彩 | 色彩 | 分数 | |

### 0.2 明确标记为「待确认 / 可能缺口」的维度

下表基于 IQA 领域通行的属性分类（技术失真类 + 美学类两大支柱，参见 Q-Bench / Q-Bench+ 的维度划分）对照得出。**这些维度目前一律视为不具备，产品不得就其输出质量判断。**

| 缺口维度 | 领域常见性 | 对本产品的影响 |
|---|---|---|
| 清晰度 / 模糊（失焦、运动模糊、镜头模糊） | 极高频。摄影师最常问的第一个问题 | **严重缺口**。影像从业者场景下几乎必被追问 |
| 噪声 / 颗粒 | 高频 | 严重缺口。与曝光强相关（欠曝提亮必然引入噪声），不具备会削弱调优建议的严谨性 |
| 压缩伪影 / 块效应 / 带状 | 中高频，交付与传输环节关键 | 中等缺口 |
| 人脸 / 人像专项（肤色、面部清晰度、证件照可用性） | 中高频，且是最容易被 demo 观众拿来试的方向 | 中等缺口，且是 demo 高危点 |
| 视频质量 / 时序稳定性 | 另一条产品线 | 明确划为 Won't |
| AIGC 特有失真（结构错误、纹理过平滑、肢体异常） | 2024 年后高频 | 明确划为 Won't（本版） |
| 显著性 / 主体定位 | 中频，是「问题在画面哪里」的前提 | 中等缺口，直接影响「局部定位」能力（见 3.1 旅程注） |

**结论（产品层）**：我们手上是一套**偏「光影色彩 + 美学」的半覆盖能力**，技术失真侧基本空白。这决定了三件事：
1. 产品的第一人设应是「**影调与观感顾问**」，不是「全维度质检员」。对外措辞必须与此一致。
2. 「诚实声明覆盖边界」不是一个可选的加分项，而是 Must 级功能（见 6.3）。
3. 路线图 M3 的第一优先级扩展方向是接入清晰度/噪声模型，而非增加花哨交互。

## 1. 产品定位与价值主张

### 1.1 一句话价值主张

> **IQAgent 把实验室的属性级 IQA 模型，变成一个说得清「问题在哪、为什么、怎么改」且每句话都能回溯到模型证据的影像诊断顾问。**

### 1.2 对谁、解决什么

- **对谁**：① 需要在 10 分钟内理解实验室技术价值的访客/合作方/评审；② 需要对一批图做质量判断并落实到修图动作的影像从业者（摄影师、修图师、电商/图库运营、影像算法工程师）。
- **解决什么**：现状下这批模型只能「每个模型各吐一个分数」。用户拿到 6 个数字后仍然不知道：这图到底行不行、主要矛盾是什么、先改哪个、改多少、改完还有什么没被检查过。IQAgent 解决的是**从分数到决策的最后一公里**。

### 1.3 相比「直接调一堆模型 API」的增量价值

这一节是本产品是否值得做的核心论证。如果下面 5 条不成立，就不该做 agent，做个批量打分脚本即可。

| # | 增量能力 | 没有 agent 时的真实痛点 |
|---|---|---|
| 1 | **意图到属性的映射** | 用户说「这图看着不够高级」，他不知道该调哪几个模型。模型菜单把选择成本转嫁给了用户 |
| 2 | **跨属性交叉归因** | 曝光 0.42、对比 0.38、整体 0.45 三个低分，并列呈现时像三个独立问题；实际很可能是「欠曝导致对比塌陷并拖累整体观感」一个根因。归因能把 3 个待办压缩成 1 个 |
| 3 | **分数到动作的翻译** | 「白平衡 0.51」不可执行；「整体偏冷偏绿，建议色温 +250~400K、色调 +4~8 向洋红」可执行。这是从业者唯一真正要的东西 |
| 4 | **覆盖边界的主动声明** | 脚本不会告诉你「我没有检查清晰度」。用户会默认「没报问题就是没问题」，这是最危险的误导 |
| 5 | **批量的排序、聚类与共性归因** | 200 张图的 1200 个分数无法阅读。用户要的是「37 张需返工、其中 29 张共因同一处偏绿光源、建议批量预设」 |

### 1.4 demo 场景与顾问场景：要求不同，架构同源

两个场景对产品的要求**在多处是直接冲突的**，必须显式处理而不是假装一致。

| 维度 | demo（访客/评审） | 顾问（影像从业者） |
|---|---|---|
| 首要目标 | 惊艳 + 零事故 | 准确 + 可追责 |
| 延迟容忍 | 极低。首屏 > 5s 即失败，端到端 > 30s 观众出戏 | 中等。单图 60s、批量数分钟可接受，只要有进度反馈 |
| 不确定性 | 是噪音。大段「可能/不确定」削弱说服力 | 是价值。置信度与边界声明本身就是专业性 |
| 输入分布 | 不可控（观众掏出手机图）但可预置样例 | 用户真实工作流图，分布相对集中 |
| 澄清提问 | 有害。被反问会打断节奏 | 有益，但不能超过 1 轮 |
| 失败代价 | 极高且不可挽回（一次卡死抹掉全部印象） | 中等，可重试 |
| 信息密度 | 低密度、强叙事、有视觉节奏 | 高密度、结构化、可导出 |

**同架构满足的方式**：把差异**全部下沉到两个可切换层**，skill 层与归因逻辑层保持唯一实现，绝不分叉两套能力。

```
          ┌──────────────────────────────────────────┐
          │  呈现档位 Presentation Profile           │  ← 差异点 1
          │  demo  : 3 条结论 + 1 个根因 + 2 个动作  │
          │  advisor: 全维度表 + 证据 + 置信度 + 边界│
          └──────────────────────────────────────────┘
          ┌──────────────────────────────────────────┐
          │  编排策略 Orchestration Policy           │  ← 差异点 2
          │  demo  : 固定路径、全并行、硬超时 8s、   │
          │          样例结果预热缓存、禁止反问      │
          │  advisor: 计划可见可编辑、允许 1 轮澄清、│
          │          超时重试、允许串行深挖          │
          └──────────────────────────────────────────┘
          ┌──────────────────────────────────────────┐
          │  认知层（归因 / 冲突消解 / 建议）  唯一实现│
          ├──────────────────────────────────────────┤
          │  Skill 层（原子 / 编排）          唯一实现│
          ├──────────────────────────────────────────┤
          │  模型 API 层                              │
          └──────────────────────────────────────────┘
```

关键取舍：**demo 档位只做减法，不做加法**。demo 看到的每一句话都必须是 advisor 档位会说的话的子集。这保证 demo 不是一层演示用的假皮，合作方深挖时不会翻车。

## 2. 目标用户与用户故事

### 角色 A：来访评审 / 潜在合作方（技术管理者，非 IQA 专家）

**画像**：停留 10~20 分钟，关心「这套东西真的能用吗、比大模型直接看图强在哪、能接进我的流程吗」。**假设**：部分访客会主动拿自己手机里的照片来试。

| # | 用户故事 | 验收标准 |
|---|---|---|
| A1 | 作为来访评审，我想要**在一次对话内看到一张图从上传到拿到可执行结论的完整过程**，以便判断这套系统是否真的落地而非拼贴 demo | 从上传到首屏结论 ≤ 5s（P90）；端到端 ≤ 30s（P90）；结论含「1 个主要问题 + 1 个根因解释 + ≥2 个具体动作」；全过程无空白等待（有逐维度流式出现的进度） |
| A2 | 作为潜在合作方，我想要**追问「你凭什么这么说」并得到逐条可回溯的依据**，以便判断结论不是语言模型的作文 | 任一结论可展开为「属性名 + 模型分数/等级 + 模型文本（若有）」；无任何依据的结论一律不出现；人工抽检 20 条结论，无证据支撑的断言数 = 0 |
| A3 | 作为来访评审，我想要**拿自己的照片试，并在系统能力不足时得到明确承认而不是糊弄**，以便建立对团队的信任 | 上传含明显失焦/噪点的图并追问「清不清楚」时，系统明确回答「当前不具备清晰度/噪声评估能力，以下是已检查的维度 X/Y/Z」；不得出现任何对清晰度的推断性结论 |

### 角色 B：影像从业者（摄影师 / 修图师 / 电商影像运营）

**画像**：有明确交付压力，审美判断强于技术词汇，只关心「改哪、改多少、能不能批量」。**假设**：主要工作在 Lightroom/Capture One/PS 等工具内，因此建议应尽量对齐这些工具的参数语言。

| # | 用户故事 | 验收标准 |
|---|---|---|
| B1 | 作为修图师，我想要**上传一张图得到按优先级排序的问题清单和参数级调整建议**，以便直接在修图软件里动手 | 输出 ≤ 3 条优先问题并排序；每条带方向 + 量级（如「色温 +250~400K」）且标注为区间而非单点；建议中不出现无法在常见修图工具中找到的参数名 |
| B2 | 作为电商影像运营，我想要**一次提交一组图拿到「可用 / 需调整 / 需返工」的分档和返工原因聚类**，以便把人工复核量压到可控 | 批量 ≥ 50 张可完成；输出三档分布 + 每档数量 + Top 3 共性问题及其覆盖张数；可按属性排序定位最差 N 张；失败图单独列出不静默丢弃 |
| B3 | 作为摄影师，我想要**用自己的话描述模糊的不满（「看着发闷」「不够通透」）也能被正确拆成要检查的维度**，以便不必学会系统的术语 | 给定 10 条真实口语诉求样本，系统给出的评测计划与专家标注的应查维度集合 F1 ≥ 0.7；计划对用户可见；用户可增删维度后重跑 |

### 角色 C：实验室内部研究者 / 模型负责人

**画像**：关心模型在真实输入上的表现、维度之间是否一致、哪些 case 暴露模型缺陷。

| # | 用户故事 | 验收标准 |
|---|---|---|
| C1 | 作为研究者，我想要**看到各属性模型在同一张图上的原始输出以及它们相互矛盾的地方**，以便定位模型校准问题 | 提供「原始输出视图」展示每次调用的入参摘要、原始返回、耗时；冲突被显式命名（如「整体分高但曝光分低」）而非被平滑掉 |
| C2 | 作为模型负责人，我想要**把一批图跑成属性相关性与异常 case 清单**，以便决定下一个该训练哪个维度 | 批量结果可导出结构化文件；输出属性两两相关性概览与「分数分布异常/极端不一致」case 列表；含每维度调用失败率 |
| C3 | 作为研究者，我想要**新增一个属性模型后只写一个 skill 描述就能被 agent 自动纳入诊断**，以便扩展成本可控 | 新增原子 skill 后，无需修改编排 skill 的代码即可进入单图诊断流程；新维度自动出现在覆盖声明中；端到端接入 ≤ 1 人日（M3 退出标准） |

## 3. 核心用户旅程

### 3.1 旅程一：单图深度诊断（顾问档位，主路径）

场景：修图师上传一张室内人像，说「这张感觉发闷、不太通透，帮我看看」。

| 步 | 用户看到 | Agent 内部做什么 | 调用的能力 |
|---|---|---|---|
| 1 | 「已收到图，1536x2048，sRGB，JPEG」 | 受理图像，抽取尺寸/色彩空间/EXIF 摘要；做可用性校验（分辨率过低、非支持格式直接拒绝并说明） | `intake.image_profile`（无模型，纯工具） |
| 2 | 一张**评测计划卡片**：「我把『发闷/不通透』理解为：对比与层次（高）、曝光（高）、色彩饱和与通透感（中）、整体观感（中）、构图（低，仅参考）。另：你提到人像，但我不具备人脸专项与清晰度评估。要调整吗？」 | 需求拆解：口语诉求 → 属性子集 + 优先级 + 每维度的判定关注点；同时计算本次的**覆盖缺口**并前置声明 | `intent.decompose`（纯 LLM，受属性白名单约束） |
| 3 | 逐维度流式出现的结果条（先出的先显示，不等全部完成） | 按计划**并行**调用属性模型；每条结果立刻回显原始分数/等级；单点失败不阻塞整体 | `assess.exposure` / `assess.contrast` / `assess.color` / `assess.white_balance` / `assess.aesthetic_composition` / `score.overall_with_rationale` |
| 4 | 「主要矛盾：影调层次不足。曝光略偏低（0.44）叠加对比明显偏低（0.31），共同造成『发闷』；色彩本身无明显偏色（白平衡 0.68），所以不是色偏问题。」 | 交叉归因：把多个低分收敛为根因假设；识别并处理冲突（例：整体分 0.62 偏中但对比 0.31 偏低 → 标注为「局部维度拖累未被整体模型充分反映」）；生成分级置信度 | `evidence.reconcile`（纯 LLM，仅允许引用已获得的模型输出） |
| 5 | 按优先级排的 3 条动作：① 提升对比：曲线中间调下压 + 高光提亮，或对比 +12~20；② 曝光 +0.2~0.4EV；③ 通透感：去雾/清晰度 +5~10（注意：本系统不评估噪声，提亮后请自行检查噪点） | 分数到参数的翻译；量级以区间给出；对依赖缺口维度的副作用挂上显式提醒 | `advise.remediation`（纯 LLM + 规则映射表） |
| 6 | 结尾固定区块：**已检查**（曝光/对比/白平衡/色彩/美学构图/整体）；**未检查**（清晰度、噪声、压缩伪影、人脸专项）——「未检查不等于无问题」 | 从白名单与本次实际成功调用集合**自动生成**，不由 LLM 自由撰写 | `report.compose` 的固定段落 |
| 7 | 用户追问「那清晰度呢？」→ 系统拒答并给出替代路径 | 命中缺口维度 → 走拒答模板，不允许进入模型推理 | 硬性护栏（见 7.3） |

注：**当前无显著性/分割模型，因此不具备「问题在画面哪个区域」的定位能力**。所有结论是全图级。这一点必须在顾问档位明示，否则从业者会期待热力图。

### 3.2 旅程二：批量筛查与共性归因

场景：电商运营提交 120 张商品图，说「帮我挑出需要返工的，告诉我主要是什么毛病」。

| 步 | 用户看到 | Agent 内部做什么 | 调用的能力 |
|---|---|---|---|
| 1 | 「收到 120 张。3 张格式不支持已剔除（列表如下）。批量模式我默认只跑曝光/对比/白平衡/色彩/整体五个维度以控制时长，美学构图默认关闭（批量下参考价值低且耗时）。需要开吗？」 | 批量受理 + 默认维度裁剪 + 一次性告知取舍。**默认值先给出，澄清可跳过** | `intake.image_profile`、`intent.decompose`（批量模式） |
| 2 | 进度条 + 已完成张数 + 预估剩余时间 | 分批并发调用，限流，失败重试 1 次，超限进入失败清单 | 各 `assess.*` 原子 skill |
| 3 | 三档分布：可用 74 / 需调整 31 / 需返工 12；另有 3 张调用失败需重试 | 按阈值分档。**假设**：阈值需用真实数据标定，首版用专家抽样标定的经验阈值并标注为经验值（见开放问题 Q4） | `screen.batch_triage` |
| 4 | Top 3 共性问题：① 偏绿偏冷（白平衡低分）29 张；② 欠曝 17 张（与 ① 重叠 11 张）；③ 对比不足 9 张 | 在低分图上做属性共现聚类，输出覆盖张数与重叠关系（不是简单计数排序） | `screen.batch_triage` 内的共性归因子步骤 |
| 5 | 「29 张偏绿图中有 26 张 EXIF 显示同一相机同一时段 → 疑似同一灯光环境，建议做一个批量白平衡预设：色温 +300K、色调 +6」 | 结合元信息做成因推断（标注为**推断**而非检测结果）；给出批量动作而非逐张动作 | `advise.remediation`（批量模式） |
| 6 | 可下钻：点任一档位/任一共性问题 → 缩略图列表 → 单张进入旅程一 | 批量结果缓存，单图下钻复用已有分数不重复调用 | 会话内记忆（见 6.4） |
| 7 | 导出：结构化结果文件 + 一页摘要 | `report.compose` 批量档位 | |

### Must（M1 必须具备；定义「demo 能跑通的最小闭环」）

最小闭环 = **上传单图 → 计划可见 → 并行属性评测 → 交叉归因出根因 → 参数级建议 → 覆盖边界声明 → 可追问依据**。

| M-7 | 证据可追溯（任一结论可展开到模型原始输出） | A2 故事的唯一实现手段，也是反幻觉的机制保障 |

| W-6 | 多用户账号体系、权限、团队协作 | 两个首要场景都不需要；M1/M2 用单会话即可 |
| W-7 | 跨模型分数加权成一个「综合质量分」 | 各模型量纲与标定未知，加权出的数字是伪精确，且会掩盖主要矛盾（见 7.2） |
| W-8 | 开放式自主多轮规划（Deep-Research 式自由探索） | 属性空间只有 6 个已知维度，自由规划收益为零、方差极大、延迟不可控（见 6.2） |
| W-9 | 移动端原生应用 | demo 与顾问均可在桌面 Web/对话界面完成 |

## 5. Skill 清单设计（14 个）

设计原则：
- **原子 skill 与模型 API 一对一**，不在原子层做任何解释或推断，只做调用、归一化、失败处理。这样新增模型的成本恒定。
- **编排 skill 不做新判断**，只负责「调谁、并行还是串行、失败怎么办、结果怎么汇总」。
- **认知 skill 是唯一允许 LLM 推理的地方，且其输入被严格限制为已获得的模型输出 + 图像元信息**，不允许 LLM 直接看图下质量结论（见 7.3）。

### (a) 原子型 skill（直接包装模型 API）

| # | 名称 | 触发条件（用户怎么说） | 输入 | 输出 | 依赖模型 API | LLM 参与 |
|---|---|---|---|---|---|---|
| A1 | `intake.image_profile` | 任何图像进入系统时自动触发 | 图像文件/URL | 尺寸、格式、色彩空间、EXIF 摘要（相机/镜头/ISO/快门/光圈/时间）、可用性校验结果 | 无（本地工具） | 否 |
| A2 | `score.overall_with_rationale` | 「这图怎么样」「整体打个分」；也被所有编排 skill 默认调用 | 图像 | 总体分数 + 模型生成的文本解释 | 整体 IQA 模型（带文本） | 否（仅透传，不改写） |
| A3 | `assess.aesthetic_composition` | 「构图有问题吗」「好不好看」「够不够高级」 | 图像 | 美学分、构图分（**假设**两者可能为同一模型的多头输出，见 Q2） | 美学/构图模型 | 否 |
| A4 | `assess.exposure` | 「是不是太暗/太亮」「曝光对吗」「发灰」 | 图像 | 曝光分 + 方向（偏暗/偏亮/正常，**假设**方向可从分数与阈值推导，若模型不给方向见 Q3） | 曝光模型 | 否 |
| A5 | `assess.contrast` | 「发闷」「不通透」「层次少」「灰蒙蒙」 | 图像 | 对比分 + 方向 | 对比模型 | 否 |
| A6 | `assess.white_balance` | 「偏色」「偏黄/偏绿/偏蓝」「色温不对」 | 图像 | 白平衡分 + 偏色方向 | 白平衡模型 | 否 |
| A7 | `assess.color` | 「颜色不好看」「饱和度」「色彩寡淡/过艳」 | 图像 | 色彩分 | 色彩模型 | 否 |

注：A4~A7 在产品语义上高度相关但必须保持为 4 个独立 skill，因为交叉归因恰恰需要它们的**分歧**（例：曝光正常 + 对比极低 → 后期过度拉平，而非拍摄曝光问题）。合并会消灭这个信息。

### (b) 编排型 skill（组合原子 skill）

| # | 名称 | 触发条件 | 输入 | 输出 | 依赖 | LLM 参与 |
|---|---|---|---|---|---|---|
| B1 | `diagnose.single_image` | 「帮我看看这张图」「全面诊断一下」；无明确维度指向的单图请求默认走这里 | 图像 + 评测计划（来自 C1） | 各维度结果集合 + 成功/失败清单 + 总耗时 | A1~A7，按计划子集并行；硬超时后返回部分结果 | 否（纯编排） |
| B2 | `diagnose.light_color_deepdive` | 「专门看看色彩和影调」「偏色和曝光的关系」 | 图像 | 曝光/对比/白平衡/色彩四维结果 + 四者间的一致性标记（如「曝光正常但对比极低」） | A4~A7（+A1 取 ISO/曝光补偿辅助解释） | 否（一致性标记为规则判定） |
| B3 | `screen.batch_triage` | 「这一批帮我筛一下」「挑出需要返工的」「哪些不合格」 | 图像集合 + 维度子集 + 可选阈值 | 三档分流 + 每档张数 + Top N 共性问题及覆盖/重叠张数 + 失败清单 + 可排序明细 | A1 + A2/A4~A7 批量并发（美学默认关闭）；阈值为经验值 | 否（分档与聚类为规则/统计，非 LLM） |

注：共性聚类刻意**不用 LLM**，因为「29 张偏绿」必须是可复算的计数事实，不能是语言模型的印象。LLM 只在 C3 里把这个事实翻译成批量动作建议。

### (c) 认知型 skill（不依赖模型，纯 LLM 推理）

| # | 名称 | 触发条件 | 输入 | 输出 | 依赖 | LLM 参与 |
|---|---|---|---|---|---|---|
| C1 | `intent.decompose` | 每次新诉求进入时自动触发（含模糊诉求、批量诉求） | 用户原话 + 可用属性白名单 + 图像元信息 + 模式（单图/批量） | 评测计划：属性子集 + 每项优先级 + 每项关注点 + 本次覆盖缺口 + 最多 1 条可选澄清问句 + 默认假设 | 无模型调用。输出必须落在白名单内（越界即被拒） | 是（核心） |
| C2 | `evidence.reconcile` | 在 B1/B2/B3 产出结果后自动触发 | 各维度分数/等级/文本 + 失败清单 + 元信息 | 主要矛盾（≤1 个根因假设）+ 支撑证据引用 + 冲突清单与处置说明 + 分级置信度（高/中/低 + 理由） | 仅消费已得输出，**不得引入新维度判断** | 是（核心） |
| C3 | `advise.remediation` | 归因完成后自动触发；或用户直接问「怎么改」 | 归因结论 + 分数 + 元信息 + 参数映射表 | ≤3 条排序动作，每条含参数名、方向、区间量级、预期效果、以及涉及缺口维度时的副作用提醒 | 无模型；依赖一张人工维护的「属性→修图参数」映射表（**假设**由实验室与 1~2 名摄影师共同标定，见 Q5） | 是（受映射表约束） |
| C4 | `report.compose` | 诊断/批量完成后；或用户说「出个报告」「导出」 | 上述全部结构化结果 + 呈现档位 | demo 档：3 条结论 + 1 根因 + 2 动作 + 边界区块；advisor 档：全维度表 + 证据 + 冲突 + 置信度 + 动作 + 边界区块 + 可导出结构化文件 | 无模型 | 是（仅行文组织；**边界区块与分数表为模板拼装，不经 LLM 改写**） |

**Skill 总览：7 原子 + 3 编排 + 4 认知 = 14。** 未来新增属性模型只需新增一个原子 skill 并在白名单注册；B1/C1/C4 自动纳入（C-4 需求）。

## 6. 正面回答「要不要做需求拆解」以及其它高阶能力

### 6.1 结论先说

**要做，而且它是 Must。但必须做成「受约束的需求拆解」，不是开放式规划。**

### 6.2 在 IQA 顾问场景下，需求拆解具体长什么样

需求拆解在这里**不是一个开放式规划问题，而是一个受约束的映射问题**：目标属性空间是已知且有限的 6 个维度。这一点决定了它既便宜又可靠，也决定了它不该被做成自由探索。

完整链条（以 B3 故事的真实诉求为例）：

```
用户模糊诉求
  「这组片子发闷，不够通透，客户说不高级」
        │
        ▼  ① 语义落地：口语 → 属性词表
  发闷/不通透 → 对比(高) + 曝光(中) + 色彩通透感(中)
  不高级      → 美学(中) + 构图(低) + 整体观感(中)
        │
        ▼  ② 优先级与关注点：不是全量跑，而是带权重跑
  对比: 重点看是否整体偏低（后期过度拉平 vs 拍摄平光）
  曝光: 看是否欠曝拖累对比
  白平衡: 纳入（「不通透」常由轻微色偏造成）
        │
        ▼  ③ 缺口前置声明（关键一步）
  「发闷」也可能来自镜头脏污/轻微失焦/雾霾 → 属清晰度维度 → 本系统不具备
  → 在出结论前就告知，而非被追问时才承认
        │
        ▼  ④ 模型调用计划（含并发、超时、失败降级）
  并行: A5 A4 A6 A7 A2 ；A3 低优先级可被超时丢弃
        │
        ▼  ⑤ 产出契约：用户最终要拿到什么
  1 个根因 + ≤3 条参数级动作 + 批量预设可行性判断
```

**它解决什么真实痛点（三个，都很具体）**：
1. **术语鸿沟**。从业者永远不会说「请评估我的对比度指标」，他说「发闷」。不做拆解，agent 只能等用户点菜，产品退化为一个模型菜单 + 聊天皮。
2. **全量调用的噪声与延迟**。不拆解的唯一替代方案是每次跑全部 6 个模型。后果是：延迟叠加（demo 直接失败）、6 个分数并列无重点（用户仍要自己读）、与诉求无关的低分造成误导（用户问影调，你告诉他构图不行，他会觉得系统跑题）。
3. **缺口的前置暴露时机**。拆解是唯一能在「出结论之前」发现「用户真正关心的维度我们没有」的环节。没有拆解，缺口只能在用户追问时暴露，那时信任已经受损。

**不做会怎样（逐条后果）**：
- demo 层面：变成「上传 → 等 20 秒 → 6 个数字 + 一段作文」。评审的第一反应是「这和我直接问一个多模态大模型有什么区别」，而这个问题我们将无法回答。
- 顾问层面：无法承接真实语言输入，从业者试两次就放弃。
- 工程层面：全量调用使延迟与成本随模型数量线性增长，M3 接入清晰度/噪声模型后必然崩盘。
- 可信度层面：缺口只能被动暴露，A3 故事直接失败。

**但必须约束成什么样**（这是取舍，不是锦上添花）：
1. 输出是**一个结构化的评测计划**，属性名必须落在白名单内；越界项被丢弃而不是让 LLM 发明新维度。
2. 计划**对用户可见、可编辑**。这既是产品价值（用户看到系统「听懂了」），也是纠错通道。
3. **一次成型**，不做多轮迭代规划。复杂度不值得（见 6.4「计划与自我修正」）。
4. demo 档位下计划**自动采用默认值并压缩为一行展示**，不等用户确认。

### 6.3 反幻觉：为什么拆解同时是可信度机制

需求拆解产出的白名单，顺带成为护栏的执行依据：**凡不在本次计划且未成功返回结果的属性，认知层一律无权生成关于它的判断**。这把「别编造」从一句 prompt 里的祈求，变成了一条可程序化校验的约束。详见 7.3。

### 6.4 其它高阶能力的逐项判断

| 能力 | 本版判断 | 理由 |
|---|---|---|
| **澄清提问** | **要，但严格限额：最多 1 轮、必须带默认值、必须可跳过；demo 档位完全禁用** | 价值真实（「发闷」可能指对比也可能指色偏），但反问是 demo 杀手，也是从业者耐心杀手。做法是「先给默认计划 + 附一句可选澄清」，而不是「先问再做」。绝不允许连续追问 |
| **计划与自我修正** | **「计划」要；「自主多轮自我修正」不要。只做 3 个枚举触发的确定性重规划** | 属性空间只有 6 维，自由探索的信息增益接近零，但延迟与方差代价极高，且不可复现（demo 大忌）。仅在三种情况下重跑：① 关键维度模型调用失败；② 用户编辑了计划；③ 归因结论依赖一个未被调用的维度（例：怀疑「欠曝导致对比低」但曝光未在计划中 → 补调一次，且只补一次） |
| **证据冲突消解** | **要，Must 级** | 这是多模型系统的必然产物（整体分与属性分不一致、相邻属性互相矛盾），也是本产品相对单模型的核心差异化。更重要的是：**冲突被平滑掉就是幻觉的温床**。处理方式见 7.1 |
| **成本/延迟感知的模型路由（大小模型选择）** | **本版不要**。只做「固定并发档位 + 硬超时 + 优先级丢弃」 | 三个理由：① 我们尚无各模型的延迟/成本基线数据，路由策略会是凭空猜测；② 路由引入不确定性，同一张图两次结果可能不同，对 demo 和可追责都是负债；③ 现有 6 个维度全部并行的总延迟由最慢的一个决定，路由带来的收益上限很低。替代方案（低成本、高确定性）：给每个维度标优先级，超时后丢弃低优先级维度并在覆盖声明中标为「未完成」。M2 收集到延迟数据后再评估 |
| **结果可信度与置信度表达** | **要，但用分级语言（高/中/低）+ 理由，不要伪精确百分比**；模型自带置信度时才透传数值 | 顾问场景下置信度是专业性的体现。但我们不知道模型标定质量，「置信度 87%」是编的，会比不给更糟。分级依据用**可解释的规则**：维度间是否一致、分数是否落在阈值边界附近、该维度是否曾调用失败、图像是否处于疑似分布外（如极低分辨率）。demo 档位只在低置信度时显示，高置信度不显示以免噪声 |
| **会话记忆** | **要会话内（短期）；不要跨会话（长期画像）** | 会话内是刚需：批量下钻要复用已得分数、追问「那白平衡呢」要知道上文是哪张图、用户说「按刚才那个标准再看这批」要能承接。跨会话画像在本版是纯负债：demo 是一次性的，顾问场景还没有真实留存用户，偏好数据无从积累，且引入存储与隐私问题（用户上传的商业图片）。放 Could |

## 7. 关键产品决策与取舍

### 7.1 决策一：属性模型与整体模型冲突时，以谁为准

- **选项**：(a) 整体模型优先（它有文本解释，更像人话）；(b) 属性模型优先；(c) 加权融合出一个数；(d) 属性优先，且把冲突本身作为一条结论输出。
- **推荐：(d)**。归因以属性模型为准（它们更专、粒度更细、是可执行建议的唯一来源）；整体模型用作「观感总体印象」的参考与文本素材来源；当两者方向明显相反时，**不消除分歧，而是显式报告**：「整体观感尚可（0.62），但对比明显偏低（0.31）——说明这张图的问题集中在影调层次，不足以拉低整体观感，但在专业交付标准下仍需处理。」
- **理由**：冲突信息对三类用户都有价值（研究者要看到它、从业者需要知道「挑剔」的程度、评审会觉得系统诚实）。而融合成一个数会把最有信息量的部分抹掉。
- **风险**：冲突过于频繁会让输出显得摇摆、削弱 demo 说服力。**缓解**：设定冲突判定阈值（**假设**：方向相反且分差超过经验阈值才算冲突，具体值需标定）；demo 档位下冲突最多展示 1 条。

### 7.2 决策二：分数要不要直接暴露给用户

- **选项**：(a) 全暴露原始分数；(b) 完全隐藏只给文字；(c) 默认给等级 + 可展开看原始分数；(d) 融合成一个总分。
- **推荐：(c)，且明确拒绝 (d)**。默认呈现「偏低 / 偏高 / 正常」等级与方向；分数作为可展开的证据层（支撑 A2、C1 故事）；**不产出任何跨模型加权的综合分**。
- **理由**：裸分数对从业者几乎无意义且容易被误读为精度承诺（「0.31 和 0.34 差在哪」我们答不上来）；但完全隐藏会让系统失去可追责性。综合分则是伪精确的典型：量纲未对齐、标定未知、且会掩盖「单一维度严重失衡」这种最需要被看见的情况。
- **风险**：评审可能主动要求「给个总分，简单点」。**缓解**：提供「一句话总体判断 + 三档结论（可用/需调整/需返工）」作为替代，它同样简洁但不假装精确。
- 附带硬约束：**任何分数在呈现时必须带出处标签（哪个属性模型）**，绝不出现孤立的无归属数字。

### 7.3 决策三：没有对应属性模型时，agent 如何诚实应对（产品可信度底线）

这是本文档最重要的一节。**风险本质**：LLM 能看图，也非常擅长写出「背景略有噪点、边缘锐度一般」这类听起来专业、实际上毫无模型依据的句子。一旦发生，本产品的全部差异化（「我们有属性级模型」）当场失效——因为输出与随便一个多模态大模型胡说无法区分，且更具误导性，因为我们声称背后有模型。

**推荐方案：四层防御，层层可验证，不依赖 prompt 的善意。**

| 层 | 机制 | 说明 |
|---|---|---|
| 1 | **属性白名单** | 系统维护一份「当前可评估属性」清单（目前 6 项）。`intent.decompose` 的输出被校验必须落在清单内；清单外的用户诉求被路由到「缺口应答」分支，不进入推理 |
| 2 | **认知层的输入隔离** | `evidence.reconcile` / `advise.remediation` 的输入**只有已成功返回的模型输出 + 图像元信息，不包含图像本身**。LLM 看不到图，就无法凭视觉编造质量判断。这是最强的单点防御，也是为什么认知 skill 被定义为「不依赖模型」 |
| 3 | **输出的证据绑定校验** | 每条质量判断必须携带它引用的属性与数值。生成后做一次机械校验：引用的属性是否在本次成功集合内、数值是否与模型返回一致。不通过则该条被丢弃（而非重试改写） |
| 4 | **缺口应答模板 + 自动覆盖声明** | 用户追问缺口维度时，走固定模板：「我当前不具备 X 的评估能力，所以不会给出关于 X 的判断。已检查的维度是 A/B/C，其中…。如果 X 是你的关键关注点，可以 [替代路径]。」覆盖声明区块由「白名单 ∖ 本次成功集合」**自动计算拼装，不经 LLM 改写** |

- **被拒绝的选项**：「在 prompt 里强调不要编造」——实践中无法保证，且无法验证，不能作为可信度底线的唯一手段。「用 LLM 的视觉判断补缺口并标注为估计」——标注会被用户忽略，且一旦被发现与事实不符，损害远超收益。
- **残余风险**：LLM 仍可能在措辞中夹带隐含判断（如用「这张画质不错」暗示清晰度没问题）。**缓解**：建立禁用词表（清晰/锐利/噪点/模糊/伪影/肤色等缺口相关词），在输出后做关键词扫描告警；并把这类 case 纳入回归用例集。

### 7.4 决策四：demo 失败兜底策略

- **选项**：(a) 失败就重试并让观众等；(b) 全程用预录视频；(c) 三级降级；(d) 只允许用预置样例图。
- **推荐：(c) 三级降级 + 强烈建议的 demo 流程设计。**

| 级别 | 触发 | 行为 | 观众感知 |
|---|---|---|---|
| L0 正常 | 全部维度在超时内返回 | 完整流程 | 正常 |
| L1 部分降级 | 部分维度超时/失败 | 用已返回维度出结论，失败维度进入「未完成」并在覆盖声明中列出；归因照常但置信度降为「中」 | 几乎无感，且显得诚实 |
| L2 缓存降级 | 超过半数维度失败 | 若为预置样例图 → 直接使用预热缓存结果并**明确标注为缓存结果**；若为观众图 → 转为「当前后端波动，我用一张预置样例演示完整流程，随后再试你的图」 | 流程不断 |
| L3 硬失败 | 服务不可达 | 切到离线样例报告（真实历史产出的静态版本），明确说明是离线样例 | 有损但不崩 |

- **理由**：demo 的失败代价不对称（一次卡死 = 全部印象），所以要买保险；但全程预录（选项 b）会被有经验的评审看穿，且丧失「现场试你的图」这个最强说服点。
- **风险**：标注「缓存结果」可能被评审视为作弊。**缓解**：把降级设计本身作为演示内容的一部分主动说明——「系统有三级降级，demo 现在走的是 L1」。这在技术评审面前通常是加分项。
- **配套要求（Must）**：3~5 张预置样例图必须覆盖「明显欠曝」「明显偏色」「影调平淡但构图好」「高质量对照」四类，且结果预热缓存；demo 前做一次全链路 health check。

### 7.5 决策五：要不要给出「综合结论/放行判断」

- **选项**：(a) 只描述问题不下判断；(b) 给三档判断（可用/需调整/需返工）；(c) 给百分制总分。
- **推荐：(b)**，并**明确标注判断依据的阈值是经验值**。
- **理由**：从业者需要一个可行动的 verdict（B2 故事的分档依赖它），但百分制总分是 7.2 已否决的伪精确。三档的好处是它本身就承认了粒度有限。
- **风险**：阈值未经真实数据标定，可能系统性偏松或偏紧。**缓解**：首版阈值由专家对 ≥100 张图抽样标定（**假设**可以组织到这个标注量，见 Q4）；阈值在产品中可调并记录版本；输出中显示「按当前标准（v1，偏严）」。

### 7.6 决策六：「需求拆解」的计划要不要让用户确认

- **选项**：(a) 必须确认后才执行（稳妥）；(b) 完全不展示，直接执行（快）；(c) 展示 + 默认直接执行 + 允许事后编辑重跑。
- **推荐：(c)**。计划卡片先展示，同时立即开始执行；用户若不干预就一路到底；编辑计划则重跑（仅重跑增量维度，已得结果复用）。
- **理由**：(a) 在 demo 中是致命的（多一次人工点击 + 多一次等待）；(b) 丢掉了「系统听懂了」这个最廉价的信任建立点，也丢掉了纠错通道。
- **风险**：用户可能在结果已出后才发现计划理解错了，产生返工感。**缓解**：计划卡片置于结果上方常驻可见；错误理解的高频 case 沉淀进 `intent.decompose` 的样例集。

### 7.7 决策七：术语层级（对谁说什么话）

- **选项**：(a) 统一用专业术语；(b) 统一用大白话；(c) 双轨：结论用生活化语言、动作用工具参数语言。
- **推荐：(c)**。问题描述用「发闷、层次不足、偏冷」；调整动作用「对比 +12~20、色温 +300K」并尽量对齐主流修图工具的参数命名（**假设**以 Lightroom 参数体系为基准，见 Q6）。
- **理由**：两类用户（评审看得懂生活化描述、从业者要能直接动手）的需求恰好分别落在这两层，不需要做人群识别。
- **风险**：参数名与用户实际工具不一致造成困惑。**缓解**：动作中注明基准工具；量级一律给区间并说明「按你的工具等效调整」。

## 8. 成功指标

原则：每个指标写清**怎么测、在什么样本上测**。不可测的指标（如「用户满意度提升」「系统更智能」）一律不列。

### 8.1 demo 效果类

| 指标 | 可测量定义 | 目标（M1 退出） |
|---|---|---|
| 首屏结论延迟 | 从图像提交到第一条维度结果可见的时间，在 20 张预置样例上各跑 5 次取 P90 | ≤ 5s |
| 端到端完成延迟 | 到完整报告渲染完成，同上取 P90 | ≤ 30s |
| 无降级完成率 | 在 50 次连续演练中达到 L0 的比例 | ≥ 85%（L0+L1 ≥ 98%） |
| 演示中断次数 | 每场 demo 中出现「需要主持人手动解释或重来」的次数，人工记录 | 每场 ≤ 0.5（即平均两场最多 1 次） |
| 结论可复述率 | demo 后立即请观众用一句话复述系统给出的主要问题与建议动作，与系统输出语义一致即算通过；样本 ≥ 10 人 | ≥ 80% |
| 自带图成功率 | 观众自带图能走完 L0/L1 流程的比例 | ≥ 90%（统计 ≥ 20 张） |

### 8.2 诊断质量类

需要一个固定的**评测集**（**假设**：200 张图，覆盖 6 维度的典型问题 + 正常对照，由 1~2 名专家标注「主要问题 + 应做调整」，见 Q4）。

| 指标 | 可测量定义 | 目标 |
|---|---|---|
| 主要问题命中率 | 专家标注的 top-1 问题出现在 agent 输出的 top-2 结论中的比例 | ≥ 75%（M2） |
| 归因精炼度 | agent 输出的问题条数 ≤ 3 且根因唯一的比例 | ≥ 90% |
| 动作可执行率 | 专家逐条判定「按此建议在修图工具中操作可改善该问题」的比例 | ≥ 80% |
| 动作量级合理率 | 专家判定建议区间未明显过量/不足的比例 | ≥ 70% |
| **无证据断言率（幻觉率）** | 抽检 100 条输出中的质量断言，统计无法回溯到具体模型输出的条数 / 总条数 | **= 0（硬性，任何非零都算阻塞缺陷）** |
| 缺口诚实率 | 用 30 条针对缺口维度的追问（清晰度/噪声/人脸/伪影）测试，正确声明不具备能力且未给出任何推断判断的比例 | **= 100%（硬性）** |
| 禁用词告警率 | 输出中出现缺口维度相关词汇（清晰/锐利/噪点/模糊/伪影/肤色）的条数，自动扫描 | 0 条未经豁免的出现 |
| 意图拆解一致性 | 10~20 条口语诉求样本上，计划属性集合 vs 专家标注集合的 F1 | ≥ 0.7 |
| 批量分档一致性 | 批量三档结果与专家分档的加权 Kappa（≥50 张样本） | ≥ 0.6（M2） |

### 8.3 工程类

| 指标 | 可测量定义 | 目标 |
|---|---|---|
| Skill 调用成功率 | 每个原子 skill 的 (成功返回 / 总调用)，按 skill 分别统计，滚动 7 天 | ≥ 99% |
| 模型 API 延迟 | 每个属性 API 的 P50 / P90 / P99，按 skill 分别记录 | P90 ≤ 3s（需基线后调整，见 Q7） |

## 9. 风险与缓解

### 9.1 高危风险（会直接决定产品成败）

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **LLM 幻觉出模型并未给出的质量判断** | 摧毁全部差异化与可信度。最严重风险 | 7.3 的四层防御；认知层不接触图像本身是核心手段；禁用词扫描；反幻觉回归用例作为发布门禁；指标 8.2「无证据断言率 = 0」为阻塞级 |
| R2 | **属性模型本身准确率未知** | 比幻觉更隐蔽：输出形式完全合规、可回溯，但结论是错的。顾问场景下会导致用户照着错建议改图 | 上线前必须在评测集上测各维度与专家标注的一致性（见 Q1）；一致性低的维度**降级为「参考」并在输出中标注**，不参与根因判定；置信度规则纳入「该维度历史一致性」 |
| R3 | **属性覆盖缺口被用户追问** | 高概率发生（清晰度是摄影师第一问）；处理不当即失信 | 缺口在 `intent.decompose` 阶段**前置声明**而非被动承认；固定拒答模板 + 替代路径；demo 话术预演清晰度/人像两个高频追问；对外材料统一定位为「影调与观感顾问」，不宣称全维度 |
| R4 | **API 延迟导致 demo 卡顿** | demo 失败代价不可逆 | 全维度并行而非串行；每维度硬超时（**假设** 8s）+ 优先级丢弃；流式分段呈现（先到先显）；预置样例结果预热缓存；7.4 三级降级；demo 前全链路 health check；**建议 demo 机器与模型 API 同网段**（工程项，需架构确认） |

### 9.2 其它需要纳入跟踪的风险

| # | 风险 | 缓解 |
|---|---|---|
| R5 | DeepSeek harness 上 skill 加载 / 工具调用 / 上下文管理需自建，工程不确定性高 | M1 刻意把 skill 数量和编排复杂度压到最低（6 原子 + 1 编排 + 4 认知即可跑通闭环）；不做自主多轮规划，降低对 harness 能力的依赖（这也是 6.4 否决自由规划的第二个理由） |
| R6 | 观众自带图落在模型训练分布外（截图、漫画、AIGC 图、极低分辨率） | `intake.image_profile` 做分布外预筛（分辨率/长宽比/是否疑似截图或插画），命中则前置提示「此类图像超出模型设计范围，结果仅供参考」；demo 引导优先使用照片 |
| R7 | 上下文膨胀（批量场景下数百张图的分数进入对话上下文） | 批量结果存在会话外的结构化结果集中，上下文只保留摘要与指针；报告生成读结果集而非上下文 |
| R8 | 调优建议与缺口维度冲突造成实际损害（建议提亮 → 噪点爆炸，而我们不评估噪声） | `advise.remediation` 对每条涉及缺口维度副作用的建议**强制挂提醒**；提醒文本为模板，不由 LLM 自由生成 |
| R9 | 用户上传商业图片的隐私与留存 | 本版不做跨会话存储（6.4 已否决长期记忆）；明确会话结束即清理策略（需与负责人确认合规口径，见 Q9） |
| R10 | 两档呈现随时间分叉，demo 档出现 advisor 档没有的说法 | 把「demo 档输出必须是 advisor 档的子集」写成回归用例：同一张图两档跑一遍，检查 demo 档每条结论都能在 advisor 档中找到对应 |

## 10. 分期路线图

### M1：demo 可跑（目标：能对着访客完整演示一次单图诊断且不出事）

- **交付物**
  - 7 个原子 skill（A1~A7）+ `diagnose.single_image` + 4 个认知 skill
  - 受约束的需求拆解 + 可见的评测计划卡片（不阻塞执行）
  - 交叉归因（1 根因）+ 参数级建议（≤3 条）
  - 覆盖边界自动声明 + 缺口硬性拒答 + 禁用词扫描
  - 证据可追溯视图（点开看原始模型输出）
  - demo / advisor 两档呈现切换
  - 三级降级 + 3~5 张预置样例（含预热缓存）
  - 反幻觉回归用例集（≥20 条）与 demo 演练记录
- **退出标准**
  1. 首屏 ≤ 5s (P90)、端到端 ≤ 30s (P90)
  2. 50 次连续演练 L0 ≥ 85%、L0+L1 ≥ 98%
  3. **无证据断言率 = 0，缺口诚实率 = 100%**（硬门禁）
  4. ≥ 3 场内部模拟 demo（含 1 场由不熟悉项目的同事扮演挑刺评审），中断次数 ≤ 0.5/场
  5. 所有 6 个维度至少完成一次与专家标注的一致性抽测，低一致性维度已降级标注（R2）

### M2：顾问能力成型（目标：一个真实从业者愿意把它用进一次真实交付）

- **交付物**
  - 批量筛查全链路（`screen.batch_triage` + 共性归因 + 下钻 + 导出）
  - 单轮澄清提问（带默认值、可跳过；demo 档禁用）
  - 分级置信度（含「该维度历史一致性」因子）
  - 冲突显式呈现与消解说明（从 M1 的「标注」升级为「解释与取舍」）
  - 研究者视图（原始输出、耗时、失败率、属性相关性概览、异常 case 清单）
  - 会话内记忆与结果缓存
  - 评测集（≥200 张，专家标注）与三档阈值标定 v1
  - 延迟/成本基线数据采集（为 M3 的路由决策提供依据）
- **退出标准**
  1. 主要问题命中率 ≥ 75%、动作可执行率 ≥ 80%
  2. 批量 ≥ 50 张可稳定完成，吞吐 ≥ 20 张/分钟，分档 Kappa ≥ 0.6
  3. ≥ 3 名真实从业者各完成一次真实任务（单图 + 批量各一），并给出结构化反馈
  4. 意图拆解一致性 F1 ≥ 0.7
  5. M1 的两条硬门禁持续为 0 / 100%

### M3：可扩展与开放（目标：补齐关键缺口，且新模型接入不再是产品问题）

- **交付物**
  - 新属性模型的声明式接入（写 skill 描述 + 注册白名单即生效，编排与覆盖声明自动适配）
  - **接入清晰度 / 噪声模型（第一优先级缺口）**；若实验室尚无则明确为外部依赖或训练需求
  - 基于 M2 基线数据评估并决定是否引入大小模型路由
  - 对比模式（改前改后 / A-B 选优）
  - 中英双语（若 Q8 确认需要）
  - 对外接口形态（供合作方试用的方式，具体形式待定）
- **退出标准**
  1. 新增一个属性模型端到端接入 ≤ 1 人日，且无需改动编排 skill
  2. 新维度自动出现在评测计划、诊断结果、覆盖声明三处
  3. 清晰度/噪声（或其替代方案）有明确结论：已接入 / 已立项 / 明确不做并更新对外定位
  4. 全部回归用例通过率 100%

### 附：本文档的三条核心主张（供快速复述）

1. **这个产品的护城河不是「调了很多模型」，而是「从分数到可执行动作的归因链条」+「每句话都能回溯到证据」**。后者一旦失守，前者毫无意义。
2. **需求拆解要做，但做成受约束的映射（6 维白名单内的一次性计划），不做开放式自主规划**。属性空间有限，自由探索收益近零、代价极高。
3. **Must 的边界就是「单图闭环 + 反幻觉护栏」**。批量、澄清、置信度、路由、记忆全部可以等；唯独「不编造」和「demo 不卡死」不能等。
